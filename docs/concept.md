# penusta-ticket 構想

## 世界観

架空のサッカースタジアム「ペヌソニックスタジアム（通称: ペヌスタ）」のチケット販売サイト。
ホームクラブは架空クラブ（名称未定、シードデータ上は「ペヌスタFC」仮）。
モデルはパナソニックスタジアム吹田。4スタンド（メイン/バック/北/南）、指定席と
ゴール裏自由席の混在、約40,000席規模。

## 目的

遊び場のハコ。ちゃんとしたチケットサイトを作りつつ、以下の遊びに拡張していく。

- UI/UX の作り込み実験（座席図、購入フロー）
- ホーム/アウェー割当・緩衝帯の設定変更を管理画面でいじる
- 販売方式（先着/抽選/waiting room）の差し替え実験
- データ分析（AWS DEA/MLA 学習素材）: 需要予測、ファネル分析、動的価格

## 設計方針

1. **スタジアム構造はデータ駆動**: スタンド→ブロック→席をマスタデータ化。
   割当・緩衝帯は「試合×ブロックへの属性」として設定テーブルで表現する。
2. **イベントログを最初から吐く**: 閲覧/カート/購入/入場を events に append-only 記録。
   分析遊びの原資。エクスポートは S3 互換形式（JSON Lines/Parquet + Hive パーティション
   `dt=YYYY-MM-DD/`）で MinIO へ。実 AWS へは同じファイルを sync するだけで移行可能。
3. **販売方式は Strategy として差し替え可能に**: sale_phases の method で表現。
4. **合成データはシナリオ付き生成器**: 一様乱数でなく分布ルールを仕込む
   （ゴール裏=20-40代男性多め、ビッグマッチは先行完売、等）。分析すると「答えが出る」データにする。

## 主要な設計判断

- **DB は PostgreSQL**: 分析系機能（ウィンドウ関数/JSONB/パーティショニング）と
  Redshift（Postgres 方言）との相性を優先。会社は MySQL だが遊び場で重複させない。
- **割当テンプレートはコピー展開方式**: 試合作成時にテンプレを match_block_allocations へ
  コピー。試合単位の個別調整（この試合だけ緩衝帯拡大）が可能で、当時の配置が履歴に残る。
- **価格はスナップショット方式**: match_prices に試合ごとの価格を持つ。
  動的価格導入時に価格履歴がそのまま学習データになる。
- **二重販売防止**: 指定席は tickets(match_id, seat_id) のユニーク制約が最後の砦。
  自由席は capacity カウントの同時実行制御（SELECT FOR UPDATE vs Redis カウンタの比較実験ネタ）。
- **仮押さえ**: 初期は DB の expires_at 方式。Redis TTL 版は後で比較実験。
