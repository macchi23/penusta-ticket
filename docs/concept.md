# penusta-ticket 構想

## 世界観

架空のサッカースタジアム「ペヌソニックスタジアム（通称: ペヌスタ）」のチケット販売サイト。
ホームクラブは架空クラブ（名称未定、シードデータ上は「ペヌスタFC」仮）。
モデルはパナソニックスタジアム吹田。4スタンド（メイン/バック/北/南）、指定席と
ゴール裏自由席の混在。ペヌスタ自体は約 20,000 人（長居の球技場くらい。メイン・バック 12,000 / ゴール裏 8,000）。

## 目的

遊び場のハコ。ちゃんとしたチケットサイトを作りつつ、以下の遊びに拡張していく。

- UI/UX の作り込み実験（座席図、購入フロー）
- ホーム/アウェー割当・緩衝帯の設定変更を管理画面でいじる
- 販売方式（先着/抽選/waiting room）の差し替え実験
- データ分析（AWS DEA/MLA 学習素材）: 需要予測、ファネル分析、動的価格

## 設計方針

1. **スタジアム構造はデータ駆動**: スタンド→ブロック→席をマスタデータ化。
   割当・緩衝帯は「試合×ブロックへの属性」として設定テーブルで表現する。
2. **イベントログを最初から吐く**: 閲覧/カート/購入/入場を events に append-only 記録。
   分析遊びの原資。エクスポートは S3 互換形式（JSON Lines/Parquet + Hive パーティション
   `dt=YYYY-MM-DD/`）で S3 互換ストレージ（ローカルは RustFS）へ。実 AWS へは同じファイルを sync するだけで移行可能。
3. **販売方式は Strategy として差し替え可能に**: sale_phases の method で表現。
4. **合成データはシナリオ付き生成器**: 一様乱数でなく分布ルールを仕込む
   （ゴール裏=20-40代男性多め、ビッグマッチは先行完売、等）。分析すると「答えが出る」データにする。

## 主要な設計判断

- **DB は PostgreSQL**: 分析系機能（ウィンドウ関数/JSONB/パーティショニング）と
  Redshift（Postgres 方言）との相性を優先。
- **割当テンプレートはコピー展開方式**: 試合作成時にテンプレを match_block_allocations へ
  コピー。試合単位の個別調整（この試合だけ緩衝帯拡大）が可能で、当時の配置が履歴に残る。
- **価格はスナップショット方式**: match_prices に試合ごとの価格を持つ。
  動的価格導入時に価格履歴がそのまま学習データになる。
- **二重販売防止**: 指定席は tickets(match_id, seat_id) のユニーク制約が最後の砦。
  自由席は capacity カウントの同時実行制御（SELECT FOR UPDATE vs Redis カウンタの比較実験ネタ）。
- **仮押さえ**: 初期は DB の expires_at 方式。Redis TTL 版は後で比較実験。

## ロードマップ（遊びの種）

- [x] ハコ: docker 環境 + スキーマ + シード + 座席図表示（初回構築）
- [x] 購入フロー（カート/仮押さえ/決済モック）— 骨格。DB 方式のみ。Redis 版との比較は未着手
- [x] 管理画面: 割当・緩衝帯エディタ（2026-10-06）。座席図の上で塗って保存。チケットのあるブロックは変更拒否、購入側と allocation 行のロックで直列化、変更は監査表へ（dev-notes.md「割当エディタ」）
- [x] 販売フェーズ（FC 先行/一般）と資格判定、年パス固定席の発行（2026-10-11）。`sale_phases` は試合ごとの行（[starts_at, ends_at)）、`SaleGate` がフェーズと会員資格（JST 暦日）を hold 時と checkout 時に判定し、checkout で `orders.sale_phase_id` を記録。販売方式は `SaleMethodRegistry` で method から引く。年パス先行は作らない（年パスは開幕前だけ販売・年間有効・途中解約なし）。固定席は `season_pass_seats` に持ち、試合ごとに paid・0 円のチケットとして発行して「販売済み」にする（`SeasonPassIssuer`）。席割りと残席は購入できる人（販売中・資格あり・ログイン済み）にだけ返し、それ以外はブロック分けだけ（座席 API は 403 `seats_hidden`、seatmap の available は null）
- [x] リセール（通常販売とは別経路）（2026-10-13）。来場できない試合の券を 1 枚ずつ出品し、買い手は出品を 10 分仮押さえしてから決済画面で確定する（`ResaleService` / `ResaleCartService`、dev-notes.md「リセール」）
  - 対象は年パスの発行分と通常購入の券。リセールで買った券は再出品不可。解約したい年パス会員は残り全試合を 1 枚ずつ出品する
  - 期間は一般販売の開始〜キックオフ 150 分前。価格は出品者が 500 円〜定価で決める（定価 = 購入価格、年パス券は大人価格 × (1 − 年パス割引率 0.25) で、年パスを単券価格で売り抜けられないようにする）。手数料は J リーグ準拠（出品者 10% + 送金 330 円、購入者 220 円）で config 化。買い手の券種は出品券を引き継ぐ（年パス券は大人）
  - 一覧は試合ページのリセール欄（ログイン済み・期間内だけ）。マイチケット（`/tickets`）から出品・取り下げ
  - 生成器: 年パスと通常購入の不参加分が出品し、一次の買い手の一部と完売のあふれ需要が安い出品を買う。calibration で出品率・成約率を見る
  - [x] リセール用カート（2026-10-13）。一次のカートとは別に `resale_holds` で 1 人 1 試合 1 件を 10 分仮押さえ（他人の一覧から消え、出品者は取り下げ不可）→ 一次と同じ見た目の決済画面 → 確定。同じ出品の押さえ直しは 30 分のクールダウン。旧即時購入のエンドポイントは削除
- [ ] 抽選販売、waiting room（Redis/キュー）
- [x] イベントログの S3 互換ストレージ（RustFS）へのエクスポート → DuckDB ローカル分析（`events:export` + `scripts/analytics.sh`）
  - [ ] dbt によるモデリング
- [x] 実 S3 + Glue/Athena パイプライン（DEA 対策）（2026-10-05）。CDK（`infra/`）で S3 + Glue + Athena WorkGroup を us-east-1 に作り、raw / curated を sync して funnel を照合、片付けまで実施（手順は dev-notes.md「実 AWS」）
  - リージョンは us-east-1 か us-west-2（レイテンシ不問、単価が安く新機能が早い）。常時課金のサービス（MWAA、EMR、Redshift プロビジョンド）は使わない
