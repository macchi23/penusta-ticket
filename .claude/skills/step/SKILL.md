方針と完了条件が決まっている 1 ステップを、CLAUDE.md の「標準の流れ」の 4〜8 に沿って進める。調査や設計判断が残っているなら先に `Explore` / `researcher` を使い、このスキルは使わない。

## 1. implementer に渡す

- モデルは CLAUDE.md の「呼び出し時のモデル上書き」で決める
- ブリーフに書くこと: 目的 / 完了条件 / 対象ファイル / 仕様（判断済みの値まで）/ 既知の制約と除外済みの仮説 / 検証方法 / 返却形式
- 実機での確認（コマンドの実行、DB や ストレージの状態）が完了条件なら、手順と期待値をブリーフに書く
- 開発 DB やストレージへの破壊的な操作は、ユーザーの承認を得てからブリーフに「承認済み」と明記して渡す
- 同じファイルを触る implementer を並列に走らせない

## 2. verifier

- `scripts/check.sh all`（E2E が対象なら `e2e` も）。implementer の check 結果だけで済ませない

## 3. レビュー

- `code-reviewer` に仕様と diff の範囲だけを渡す。implementer の説明は渡さない
- 認証・認可、決済、ユーザー入力の受け口、管理画面、同時実行制御に触れたら `security-reviewer` も並列で
- 販売の整合性に関わる変更はレビューを fable に上げる
- verifier とレビューは並列に走らせてよい（レビューは読み取りのみ）

## 4. 差し戻し（最大 2 往復）

- 重大・中は必ず戻す。軽微は安く直せるなら戻す。数行の自明な修正ならメインが直してよい
- 2 往復目でも残る軽微な指摘は、報告に残してコミットへ進む
- 同じ指摘で 2 回差し戻したら implementer を opus に上げる

## 5. コミット前の確認

- implementer が「一時的に壊して戻した」と報告した変更は、`git diff` と実際のコマンド実行で戻っていることを確かめる
- 修正後に verifier をもう一度通す

## 6. コミット

- そのステップのファイルだけを `git add` する（他ステップの未コミット変更を混ぜない）
- メッセージは 1 行目に「対象: 何をしたか」、本文に理由を 2〜3 行
- ドキュメント（dev-notes の手順・申し送り、concept のロードマップ、dea-notes）の更新は、最後のステップか別のドキュメント用コミットにまとめる

## 7. 報告と台帳

- ユーザーには、コミット ID、check の結果、レビュー結果（重大の有無と、対応した指摘）、ブリーフから外れた判断を短く伝える
- サブエージェントの「ハーネスへの気づき」は `docs/harness-backlog.md` に転記する
